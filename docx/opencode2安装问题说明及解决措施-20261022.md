# OpenCode2-node 安装问题说明及解决措施（2026-10-22）

> [!IMPORTANT]
> **⚠️ 历史阶段性记录更正声明（2026-11-01）**：
> 本文档下文记录的“Bun 版 OpenCode 在 Win7 兼容层下无法运行（无法修复）”、“必须切换至 Node 版”为早期未深入反汇编时的阶段性推测结论，**现已彻底推翻并已在 VxKex NEXT 中完美修复**！
> - **真凶定位**：Bun 运行时报 `ENOTSUP` 并非内核驱动缺陷，而是 `uSockets` 在 `recv()` 中硬编码传入 Windows 8+ 新增标志位 `MSG_PUSH_IMMEDIATE (0x20)` 触发 Win7 原生 `WSAEOPNOTSUPP (10045)` 导致，且其延迟加载的 `wsock32.dll` 此前未纳入重写白名单；
> - **修复状态**：VxKex NEXT 现已在 `KxNet.dll` 中原生过滤 `0x20` 标志，并在 `KexDll.dll` 中强制重写 `wsock32.dll`。Bun 原生版（如 `@opencode/cli`）在 Windows 7 下网络与服务端均可 100% 正常运行，**无需再安装或使用 Node 临时过渡版**。
> - **相关深入分析**：详见 [`docx/Bun在Win7下ENOTSUP与网络失败根因逆向分析-20261101.md`](Bun在Win7下ENOTSUP与网络失败根因逆向分析-20261101.md) 与 [`docx/VxKex-NEXT修复Bun网络兼容性设计方案-20261101.md`](VxKex-NEXT修复Bun网络兼容性设计方案-20261101.md)。

## 一、现象与问题描述

在 Windows 7 SP1 x64（配置 VxKex NEXT 兼容层）环境下，在终端执行 `opencode2-node --version` 时报错中断：

```text
PS D:\project\VxKex-NEXT> opencode2-node --version
ResourceUnavailable: D:\project\claude-code-engineering\node-v22.22.2-win-x64\opencode2-node.ps1:14:3
Line |
  14 |    & "$basedir/node_modules/@opencode/cli-node/bin/opencode2-node.exe" …
     |    ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
     | 程序'opencode2-node.exe'运行失败： An error occurred trying to start process 
     | 'D:\project\claude-code-engineering\node-v22.22.2-win-x64\node_modules\@opencode\cli-node\bin\opencode2-node.exe' 
     | with working directory 'D:\project\VxKex-NEXT'. 
     | The specified executable is not a valid application for this OS platform.
```

核心报错：`The specified executable is not a valid application for this OS platform`（指定的执行文件不是该操作系统的有效应用程序）。

## 二、根本原因深度分析

经全面逆向排查与 PE 文件结构核验，该问题由两个层级的阻断叠加导致：

### 1. 第一层阻断：目标二进制实为 234 字节文本占位脚本（非有效 PE 文件）
- **现象溯源**：检查调用目标 `D:\project\claude-code-engineering\node-v22.22.2-win-x64\node_modules\@opencode\cli-node\bin\opencode2-node.exe`，发现其文件大小仅为 **234 字节**。
- **内容查看**：文件头部缺少 `MZ` / `PE` 签名，其实际为纯文本 shell 脚本：
  ```bash
  echo "Error: @opencode/cli-node's postinstall script was not run." >&2
  echo "" >&2
  echo "This occurs when installation scripts are disabled." >&2
  echo "Run the package postinstall script or reinstall with scripts enabled." >&2
  exit 1
  ```
- **机制机理**：NPM 模块 `@opencode/cli-node` 采用占位包设计。在安装阶段，默认由 `postinstall.mjs` 探测当前系统架构并从子包（`@opencode/cli-node-windows-x64`）中将真正的二进制程序复制/硬链接至 `bin/opencode2-node.exe`。由于安装时跳过了脚本执行或 postinstall 阶段异常，该占位符未被替换。Windows 内核加载器在解析 PE 头部失败后，直接抛出 `The specified executable is not a valid application for this OS platform`。
- **资产留存**：真正的 64 位原生可执行文件（大小约 180MB，`180,201,288` 字节）已随可选依赖完整下载于：
  `D:\project\claude-code-engineering\node-v22.22.2-win-x64\node_modules\@opencode\cli-node\node_modules\@opencode\cli-node-windows-x64\bin\opencode2-node.exe`。

---

### 2. 第二层阻断：Node.js SEA 运行时平台版本硬拦截（Windows 10 门槛）
- **架构属性识别**：对真正的 `opencode2-node.exe` 二进制进行 PE 特征分析：
  - **Machine**：`0x8664`（x64），子系统：3（Console）；
  - **运行时签名**：包含 `NODE_SEA_BLOB`、`NODE_SEA_FUSE`、`v8::`、`libuv` 等签名，表明其为 **Node.js 单文件独立可执行文件（Single Executable Application, SEA）**，而非此前基于 Bun 的程序；
  - **导入表比对**：依赖 13 个 DLL，原生 Win7 缺失的 `GetSystemTimePreciseAsFileTime` 已被 VxKex 的 `KxBase.dll` 完整导出覆盖，底层无任何 `0xc0000139` 符号缺失。
- **运行时拦截**：当直接运行该真实程序时，程序直接退出且返回状态码 `216` (`0x000000D8`)，标准错误输出：
  ```text
  Node.js is only supported on Windows 10, Windows Server 2016, or higher.
  Setting the NODE_SKIP_PLATFORM_CHECK environment variable to 1 skips this
  check, but Node.js might not execute correctly. Any issues encountered on
  unsupported platforms will not be fixed.
  ```
  这是现代 Node.js 运行时内置的平台兼容性防御校验。在未设置环境变量前，Node.js 运行时会在进程启动之初主动中断。

## 三、架构对比：Node 版 OpenCode 与 Bun 版 OpenCode 的本质差异

（**更正注：以下推论已于 2026-11-01 证伪并修复**：Bun 的真正问题是 Win8+ `MSG_PUSH_IMMEDIATE (0x20)` 未被 Win7 Winsock 支持，现已在 `KxNet.dll` 过滤修复，Bun 原生版已完全恢复正常）。

此前排查确认旧版 `opencode.exe`（v2.0.6）在 Win7 兼容层下无法运行，其根因在于 **Bun 运行时与 Win7 内核驱动的脱节**：
1. **Bun 的致命缺陷**：Bun 依赖 Win10 内核级等待完成包 `NtCreateWaitCompletionPacket`，且底层 `uSockets` 与 Win7 Winsock 驱动（`afd.sys`）状态机严重不兼容，导致入站连接握手后被服务端底层主动发送 `TCP RST`（无法修复）；
2. **Node 版的优势**：`opencode2-node.exe` 采用成熟稳定的 **Node.js + libuv** 架构。libuv 对旧版 Windows 网络模型有成熟的兼容性支持，完全不受 Bun 内核驱动断流缺陷影响。

**测试验证**：
在设置 `NODE_SKIP_PLATFORM_CHECK=1` 后，启动内置 HTTP 服务测试：
```powershell
opencode2-node serve --port 49517 --hostname 127.0.0.1
```
通过 HTTP 客户端访问 `http://127.0.0.1:49517/` 及相关 API 路由，**均稳定返回 HTTP 200**，证明其网络状态机与本地微服务架构在 Win7 + VxKex 下完全正常运作。

## 四、具体解决措施与落地实施

针对上述两个层级的阻断，已完成以下就地修复与配置：

### 1. 部署真实二进制并建立硬链接
将下载好的 180MB 真实二进制文件部署至模块的 `bin` 目录：
1. 备份原 234 字节占位脚本至 `bin/opencode2-node.exe.placeholder.bak`；
2. 建立由平台依赖包至 `bin/opencode2-node.exe` 的硬链接（SHA256: `28700FC3A546BE4B42579472A6F7577CF2AFACBD67C374ACDCC9FBDB89FF6D7E`）。

### 2. 优化启动垫片（`opencode2-node.ps1`）
为避免全局注入环境变量对系统其他进程产生干扰，针对 PowerShell 启动脚本 [opencode2-node.ps1](file:///D:/project/claude-code-engineering/node-v22.22.2-win-x64/opencode2-node.ps1) 进行了局部作用域动态适配：
1. 备份原脚本为 `opencode2-node.ps1.bak`；
2. 在脚本调用前临时设置 `$env:NODE_SKIP_PLATFORM_CHECK = "1"`，并在 `finally` 块中严格恢复用户原有的环境变量值：

```powershell
#!/usr/bin/env pwsh
$basedir=Split-Path $MyInvocation.MyCommand.Definition -Parent

$exe=""
if ($PSVersionTable.PSVersion -lt "6.0" -or $IsWindows) {
  $exe=".exe"
}
# Win7 + VxKex: Node.js SEA 运行时启动时会进行 Windows 10 平台检查。
# 仅在当前调用周期内设置绕过检查标记，并在 finally 中精准还原，不污染外部终端环境。
$__oldSkip = $env:NODE_SKIP_PLATFORM_CHECK
$env:NODE_SKIP_PLATFORM_CHECK = "1"
try {
  if ($MyInvocation.ExpectingInput) {
    $input | & "$basedir/node_modules/@opencode/cli-node/bin/opencode2-node.exe" $args
  } else {
    & "$basedir/node_modules/@opencode/cli-node/bin/opencode2-node.exe" $args
  }
} finally {
  $env:NODE_SKIP_PLATFORM_CHECK = $__oldSkip
}
exit $LASTEXITCODE
```

## 六、已知边界与后续使用注意事项

1. **NPM 重新安装覆盖风险**：
   若后续通过 `npm install -g` 重新安装或升级 `@opencode/cli-node` 且未开启 scripts，NPM 会再次生成占位文本并覆盖已修改的 `.ps1` 启动脚本。遇到相同报错时，需重复上述硬链接及脚本调整。
2. **`opencode2-node.cmd` 适配**：
   当前针对 PowerShell 终端环境优化了 `.ps1` 垫片；若后续需在传统 `cmd.exe` 独立终端中直接调用 `opencode2-node.cmd`，亦建议在该 `.cmd` 头部追加 `set "NODE_SKIP_PLATFORM_CHECK=1"`。
3. **功能边界验证**：
   目前已验证命令行启动、版本探测与 `serve` 本地微服务 HTTP 通信；深度交互式 TUI、模型凭据鉴权及工作区 Agent 功能有待后续实际开发中进一步业务验证。
