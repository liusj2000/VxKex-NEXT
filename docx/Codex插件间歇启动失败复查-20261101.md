## 为什么会看起来随机

### 已确认的机制

同一个监视器面对耗时不同的加载过程：及时收到 renderer_ready 就成功；超过等待预算且未收到就绪消息，就用静态错误页覆盖原 Webview。因此单纯继续等可能无法让错误页自行恢复。

12:02 和 12:56 的失败均记录 receivedWebviewMessage=false，比普通模型请求慢更靠前：宿主还没收到侧栏前端消息。后端初始化成功也不等于侧栏已启动成功。

### 资源与加载方面的线索，尚未证明唯一因果

1. 对应 renderer.log 多次记录 Extension host is unresponsive；今天各次激活都有宿主卡顿线索，成功会话也有，因此不能只凭该日志判定某次必然失败。
2. 失败会话启动阶段大量 potential listener LEAK 警告，最多约 967 个监听。栈位于 VS Code 文件 readFileStream 与 Webview 资源处理路径，值得检查并发资源读取及其释放；警告本身不能证明永久内存泄漏，也不能唯一归因给某个扩展。
3. 本机实查为 4 核、约 4 GiB 可见物理内存，采样时可用物理内存约 617 MiB；同时存在多个 Code 进程及 agy、codex。资源压力可能增加加载和调度延迟，但本次快照不等于失败发生时的内存数据，没有硬缺页/磁盘对照证明其为根因。
4. 成功性能记录显示大量时间发生在 renderer_entry_evaluated 之前：例如 12:17 那次入口约 71.2 秒才执行，renderer_ready 约 76.4 秒；13:29 那次入口约 32.1 秒，就绪约 32.2 秒。这支持优先查看资源加载、模块解析与执行排队，而非把全部耗时归给登录或模型 API。
5. 13:00:05 VS Code 记录扩展宿主 terminated unexpectedly 并自动重启，重启后 Codex 成功。main.log 对同 PID 记录退出码 0，所以不能据此指定某个崩溃异常、OOM 或 DLL 原因，也不能把该重启当作 12:56 超时的已证实原因。

本轮没有找到留存的 exthost CPU profile，无法从 CPU 采样锁定阻塞函数。当前日志也不足以确定是磁盘、脚本执行、GPU、线程调度或某个扩展造成长等待。

## 与其他已知故障的区别

- 10 月 17 日的 0xc0000139 是缺 API 导出导致 codex.exe 不能加载；今天两次主要失败有 Initialize received，不能沿用该解释。
- Codex 命令工具在沙箱内返回 0xC0000142，是已记录的 Win7 受限子进程问题；不能解释侧栏为什么没有 renderer_ready。
- Claude 新版 Bun ENOTSUP 是另一运行时的网络故障，与本次 Codex 前端超时没有建立因果关系。
- 日志有网络请求和其他扩展兼容性错误，但不能将它们直接当作本次 Webview 超时根因。

## 处理方向

当前 120 秒补丁仍有效，但只能缓解超时，不能保证稳定。不再无依据将等待改得更长。

继续解决应优先在独立诊断窗口做两项对照：

1. 保留原配置与会话，比较仅 Codex 与正常扩展组合的重复冷/热启动；记录内存、磁盘读与硬缺页、扩展宿主和 Webview CPU profile。
2. 捕获 Webview 开发者工具从页面开始到首个入口执行期间的资源瀑布和第一条脚本错误，检查本地模块读取、并发、取消和消息握手。若定位到特定扩展或兼容接口，再设计范围有限的修复。

已显示启动错误页时，保存工作后重载窗口能发起新一次加载；它是重试方法，不是根因修复。继续保留用户账号、历史会话和缓存，避免通过清空数据掩盖问题。
