# 控制台 VT 转义序列乱码分析与解决建议（2026-10-18）

## 1. 现象描述与背景

在 Windows 7 SP1 x64 环境下，通过 VxKex NEXT 运行 **PowerShell 7**（`pwsh.exe` 7.4 / 7.6.7）时，交互式终端（包括 VS Code 内置终端与独立 `pwsh.exe` 窗口）出现严重的输入与高亮显示乱码：

1. **输入行严重错位变形**：
   输入命令时，终端将 ANSI/VT 控制序列原样输出为文本字符，例如：
   ```text
   PS C:\Users\liusj> 2m$null←[0m←[37m)←[39;49m←[0m
   PS C:\Users\liusj> ←[0m←[93mRemove-Module←[0m←[39;49m ←[0m←[37mPSReadLine←[39;49
   ```
   其中 `←[93m`（亮黄前景色）、`←[37m`（白色）、`←[0m`（重置）、`←[39;49m`（恢复默认前/背景色）等控制字符没有被终端渲染引擎解析，而是作为可打印字符直接写屏，导致光标位置错乱、行编辑撕裂。
2. **排除非关键变量**：
   - 执行 `Remove-Module PSReadLine` 后，命令行恢复基本输入能力，说明问题直接发生在 **PSReadLine 模块的行编辑渲染** 与 **终端显示管线** 之间。
   - 独立运行 `pwsh -NoProfile` 问题依然复现，排除了个人 PowerShell `$PROFILE` 配置脚本的影响。
   - 核查 PSReadLine 运行状态与终端能力判定：
     ```powershell
     $Host.UI.SupportsVirtualTerminal
     # 返回: True
     $t = [Microsoft.PowerShell.PSConsoleReadLine].Assembly.GetType('PlatformWindows')
     $t.GetField('_enableVtOutput', [Reflection.BindingFlags]'NonPublic,Static').GetValue($null)
     # 返回: True
     ```
     这证实：**PowerShell 主机（ConsoleHost）与 PSReadLine 都判定当前控制台“支持 Virtual Terminal (VT) 虚拟终端输出”**，因此 PSReadLine 选择了 `VirtualTerminal` 输出引擎，向屏幕发送了大量 ANSI 转义码。

---

## 2. 根本原因深度分析（因果链路）

经过对照 Windows 7 控制台子系统规范、PowerShell / PSReadLine 官方源码（`PlatformWindows.cs`、`ConsoleControl.cs`、`ConsoleHostUserInterface.cs`）以及 VxKex 本地源码（`01-Extended DLLs\KxBase\console.c`、`conansi.c`、`file.c`），定位出 **两大核心根因**：

### 根因一：VxKex 虚假回报 `ENABLE_VIRTUAL_TERMINAL_PROCESSING` 支持

1. **Win7 原生行为**：
   虚拟终端处理标志 `ENABLE_VIRTUAL_TERMINAL_PROCESSING` (`0x0004`) 于 Windows 10 (TH2/1511) 引入。Windows 7 原生 `kernel32.dll!SetConsoleMode` 不支持该标志，传入必返回 `FALSE`，错误码 `ERROR_INVALID_PARAMETER (87)`。
2. **PSReadLine 的自适应设计**：
   在原生 Win7 下，PSReadLine 调用 `SetConsoleOutputVirtualTerminalProcessing()` 失败后，会自动降级至 `LegacyWin32Console` 引擎，使用 Windows 7 原生 Win32 Console API（`SetConsoleTextAttribute`、`SetConsoleCursorPosition` 等）进行着色和光标控制，完全正常且无乱码。
3. **VxKex 的欺骗机制**：
   `pwsh.exe` 启用了 VxKex，其 `kernel32` 导入被重定向至 `KxBase.dll`。查看 `01-Extended DLLs\KxBase\console.c`：
   ```c
   Success = SetConsoleMode(ConsoleHandle, Mode);
   if (!Success && GetLastError() == ERROR_INVALID_PARAMETER && (Mode & Mask)) {
       Success = SetConsoleMode(ConsoleHandle, Mode & ~Mask); // 剔除 0x4 后重试
       Emulated = Success;
   }
   if (Success) {
       KxConsoleModes[Slot].VirtualMode = Emulated ? (Mode & Mask) : 0;
   }
   ```
   并在 `Ext_GetConsoleMode` 中：
   ```c
   *Mode |= KxConsoleModes[Index].VirtualMode;
   ```
   `KxBase` 吃掉了 `ERROR_INVALID_PARAMETER` 并向调用方返回 `TRUE`，回读时又虚假补充 `0x0004` 位。这直接误导了 PowerShell 和 PSReadLine，使其坚信宿主是支持 VT 序列的现代终端（如 Windows Terminal），从而进入 `VirtualTerminal` 发送模式。

---

### 根因二：句柄不匹配（Handle Mismatch）导致内置 ANSI 模拟器被绕过

VxKex 内部其实集成了一个初始版本的 ANSI 序列模拟器（`conansi.c`），当检测到 VT 模式时理应拦截 `WriteConsole` 并将 ANSI 序列转换为 Win32 控制台属性。但由于句柄匹配逻辑缺陷，该模拟器 **完全未被触发**：

1. **PSReadLine / ConsoleHost 的取句柄方式**：
   查看 PSReadLine `PlatformWindows.cs` 第 329~349 行与 PowerShell `ConsoleControl.cs` 第 556~578 行：
   为避免标准输出重定向影响物理控制台配置，两者均显式调用：
   ```csharp
   CreateFile("CONOUT$", GENERIC_READ | GENERIC_WRITE, FILE_SHARE_WRITE, ..., OPEN_EXISTING, ...)
   ```
   打开了一个全新的控制台活动屏幕缓冲区句柄（设句柄数值为 `H_conout`，例如 `0x1F`），并在 `H_conout` 上调用 `SetConsoleMode`。因此 `KxConsoleModes` 记录的句柄键值是 `H_conout`。
2. **.NET 输出时的句柄**：
   当 PSReadLine 通过 `Console.Write` / `Console.Out` 输出高亮文本时，.NET 底层实际写入的是标准输出句柄：
   ```csharp
   GetStdHandle(STD_OUTPUT_HANDLE)
   ```
   （设句柄数值为 `H_stdout`，例如 `0x07`）。虽然两者指向同一个物理屏幕缓冲区，但**句柄数值不同**（`H_stdout != H_conout`）。
3. **致命的逐句柄比较过滤**：
   在 `01-Extended DLLs\KxBase\console.c`（commit `8458fd5` 引入）：
   ```c
   STATIC BOOLEAN KxBasepHasEmulatedAnsiOutputLocked(IN HANDLE ConsoleHandle OPTIONAL)
   {
       for (Index = 0; Index < ARRAYSIZE(KxConsoleModes); ++Index) {
           ...
           if (ConsoleHandle && KxConsoleModes[Index].Handle != ConsoleHandle) {
               continue; // 0x07 != 0x1F，直接跳过！
           }
           if (KxConsoleModes[Index].VirtualMode & ENABLE_VIRTUAL_TERMINAL_PROCESSING) {
               return TRUE;
           }
       }
       return FALSE;
   }
   ```
   当 `Ext_WriteConsoleA/W`（以及 `Ext_WriteFile`）接收到 `H_stdout` 时，`KxBasepShouldProcessConsoleAnsi` 判定该句柄**未开启 VT 模式**！
4. **最终穿透到 Win7 原生控制台**：
   `Ext_WriteConsole` 跳过了 `WriteConsoleWithEscapeSequencesAorW`，原样直传给 Windows 7 原生 `kernel32!WriteConsole`。Windows 7 conhost 根本不认识转义序列，直接将 `\x1b[93m` 等原始控制字节绘制在屏幕上，导致乱码。

## 3. 解决建议与修复方案

### 3.1 用户环境临时应急绕开（无需重新编译）

如果需要在未更新 VxKex 的机器上立即恢复正常交互输入：

* **方法一（推荐：保持 PSReadLine 功能，仅使用纯文本渲染）**：
  在当前终端执行或写入 PowerShell 配置文件（`$PROFILE`）：
  ```powershell
  Set-PSReadLineOption -OutputMode PlainText
  ```
  PSReadLine 的补全、历史、多行编辑仍然保留，仅关闭 VT 着色，杜绝转义字符写屏。
* **方法二（移除 PSReadLine 模块）**：
  在 `$PROFILE` 中添加：
  ```powershell
  Remove-Module PSReadLine
  ```
  回退到经典控制台行输入模式。

---

### 3.2 VxKex 源码级系统修复（本次实施）

为了彻底解决此问题，在 `01-Extended DLLs\KxBase\console.c` 中实施以下改进：

1. **屏幕缓冲区状态多句柄共享（解决句柄不匹配）**：
   - 在 `KxBasepHasEmulatedAnsiOutputLocked` 中：
     - 首先按传入句柄精确匹配（优先保证显式句柄覆盖与独立配置）。
     - 若未找到显式条目且传入句柄属于控制台输出句柄（`IsConsoleOutputHandle(ConsoleHandle)`），则检查当前进程是否有任一控制台输出句柄开启了 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`。
     - 这使得 `CONOUT$` 上配置的 VT 模式能够正确作用于通过 `STD_OUTPUT_HANDLE` 写入的输出流，使 ANSI 序列模拟器正常工作，消除 `←[93m` 乱码。
   - 在 `Ext_GetConsoleMode` 中：
     - 若句柄无显式配置，且为控制台输出句柄，同样同步活动缓冲区的虚拟模式位，使组件能力查询保持一致。
2. **新增 VT 模拟全局停用开关（`VXKEX_NO_CONSOLE_VT`）**：
   - 增加环境变量检查 `VXKEX_NO_CONSOLE_VT`。
   - 当用户配置 `VXKEX_NO_CONSOLE_VT=1` 时，`Ext_SetConsoleMode` 不再剔除 `0x0004` / `0x0200`，直接穿透至 Win7 原生 `SetConsoleMode`。
   - 原生 Win7 必然返回 `ERROR_INVALID_PARAMETER`，使 PSReadLine、PowerShell 7、Python、Node.js、Rust CLI 等应用自动、平滑地降级到成熟稳定的 `LegacyWin32Console` / Win32 控制台 API，100% 杜绝任何兼容性转义异常。
3. **保持既有测试用例完全兼容**：
   - 保留 `test/conpty-review-test.c` 要求的独立句柄显式模式覆盖特性（如显式设置 `con2` 模式不会破坏已记录的显式条目）。
