# Bun 运行时在 Windows 7 兼容层下的网络实现缺陷分析及建议（2026-10-18）

> 2026-11-01 复核说明：本文保留历史观察和当时推断。“纯用户态绝对无法修复”、缺少 WaitCompletionPacket 或 afd.sys 必然导致当前故障、API Key 模式保证可用等结论，没有本次 ENOTSUP 的调用栈和完整验收支持，不应作为定论。最新实验只定位到原生 CLI 在 HTTP CONNECT 发出前失败，具体调用仍待取证。请先阅读 [新模型与 Bun 兼容修复可行性复核](ClaudeCode新模型与Bun兼容修复可行性复核-20261101.md) 及 [11 月 1 日诊断](ClaudeCode-ENOTSUP排查-20261101.md)。

## 一、背景与问题概述

随着现代 JavaScript/TypeScript 运行时的演进，**Bun** 因其极高的执行速度、内置打包器以及单文件可执行文件（Single Executable Application, SEA）特性，被越来越多新兴的 AI 终端工具（如 OpenCode CLI、Claude Code CLI 等）选为核心运行底座。

然而，在 Windows 7 SP1 x64 环境下（即便启用了类似 VxKex NEXT 这类 Win32 API 扩展兼容层），基于 Bun 构建的应用程序在执行网络操作时普遍面临严重的运行障碍，典型表现为：
1. **入站 Web 服务连接即刻被重置（`TCP RST`）**：调用 `Bun.serve()` 成功监听端口后，任何本地客户端（如 Curl、Browser、CLI 自身的前端 TUI）一旦建立 TCP 连接并发送首个 HTTP 请求，连接立即被服务端主动掐断（报 `curl: (56) Recv failure: Connection was reset`），导致所有依赖本地 HTTP/WebSocket 微服务的架构彻底瘫痪；
2. **出站网络与代理隧道连接中断**：通过 `fetch()` 发起 HTTPS 请求或通过 `HTTP_PROXY` 隧道通信时，同样频繁触发 `TypeError: Unable to connect` 或 `ECONNREFUSED`；
3. **僵尸进程与端口级联冲突**：服务进程因握手探测失败而退出，但底层套接字句柄未彻底释放，导致端口长期被占用（`EADDRINUSE`），后续运行陷入死循环。

本文通过对 Bun 内部网络子系统源码、Windows 10/7 底层网络架构代差、VxKex 运行时日志（`.vxl`）及二进制逆向证据的系统性剖析，全面揭示 Bun 在 Win7 兼容层下网络失效的深层机理，阐明纯用户态兼容层的能力边界，并提出切实可行的工程应对建议。

## 二、Bun 在 Windows 平台上的网络架构全景

要理解缺陷的本质，首先需梳理 Bun 在 Windows 上的网络栈模型：

```mermaid
flowchart TD
    subgraph AppLayer [应用层 / JavaScript 代码]
        JS["Bun.serve() / fetch() / WebSocket"]
    end

    subgraph BunCore [Bun 核心运行时 (Zig / C++)]
        JSC["WebKit / JavaScriptCore (事件循环 & 微任务调度)"]
        US["uSockets (高性能 HTTP/WebSocket 协议解析)"]
        UV["libuv (Windows 平台套接字与异步 I/O 驱动)"]
    end

    subgraph Win32User [Win32 用户态 API 兼容层 (VxKex)]
        WS2["ws2_32.dll / KxNet.dll"]
        NT["ntdll.dll / KxNt.dll"]
        K32["kernel32.dll / KxBase.dll"]
    end

    subgraph WinKernel [Windows NT 内核与系统驱动 (Ring 0)]
        AFD["\Device\Afd (afd.sys - Winsock 辅助驱动)"]
        TCPIP["tcpip.sys (TCP/IP 网络协议栈)"]
        IOCP["NT I/O Completion Port (完成端口内核队列)"]
        WCP["Wait Completion Packet (内核等待完成包机制 - Win7缺失)"]
    end

    JS --> JSC
    JSC --> US
    US --> UV
    UV --> WS2
    UV --> K32
    JSC --> NT

    WS2 --> AFD
    K32 --> IOCP
    NT -.->|Win10正常调用 / Win7未找到导出| WCP
    AFD --> TCPIP
    AFD --> IOCP
```

与 POSIX 平台（Linux 下采用 `epoll`、macOS 下采用 `kqueue`）不同，Bun 在 Windows 上的网络实现呈现以下鲜明特征：
1. **依赖 `libuv` 作为底层网络驱动**：由于 Zig 语言早期缺乏原生的 Windows IOCP 异步网络调度器，Bun 在 Windows 平台将套接字 I/O、定时器与事件循环委托给了 `libuv`；
2. **官方基准要求极高**：Bun 官方文档明确声明，Windows 原生运行必须满足 **Windows 10 Version 1809 (Build 17763) 或更高版本**；
3. **深度集成现代 NT 内核原语**：Bun 与 JavaScriptCore 不仅调用标准 Win32 Winsock API，还大量引入了 Windows 10 近年新增的内部 NT 系统调用与内核驱动特性。

## 三、五大核心网络缺陷与底层根因深度剖析

### 缺陷 1：NT 内核级等待完成包（Wait Completion Packet）缺失

这是 Bun 底层事件调度器在 Windows 7 下遭遇的**首要硬性阻断**。

#### 1. 现场抓取证据
在提取 VxKex 拦截 `opencode.exe`（基于 Bun 打包）启动时的底层调用日志中，捕获到如下记录：
```text
Failed to resolve NtCreateWaitCompletionPacket (#0) from ntdll.dll
NTSTATUS error code: STATUS_ENTRYPOINT_NOT_FOUND (0xc0000139)
Failed to resolve NtAssociateWaitCompletionPacket (#0) from ntdll.dll
NTSTATUS error code: STATUS_ENTRYPOINT_NOT_FOUND (0xc0000139)
Failed to resolve NtCancelWaitCompletionPacket (#0) from ntdll.dll
NTSTATUS error code: STATUS_ENTRYPOINT_NOT_FOUND (0xc0000139)
```
通过在目标二进制文件的 `0x4ce3bcd` 偏移处逆向排查，证实上述三个 NT 原语系由 JavaScriptCore / Bun 运行时网络调度层动态加载。

#### 2. 深层机理与内核代差
* **传统 Win32 限制**：在 Windows 7 时代，线程等待多对象（`WaitForMultipleObjects`）受制于 `MAXIMUM_WAIT_OBJECTS = 64` 的硬性约束。若需同时监控成百上千个套接字或定时器，必须创建庞大的辅助线程池，开销巨大；
* **Win10 的变革（Wait Completion Packet）**：微软在 Windows 8/10 内核中引入了等待完成包机制。通过 `NtAssociateWaitCompletionPacket`，应用程序可以将任意内核同步对象（事件、互斥体、定时器）直接挂接至完成端口（IOCP）。当目标对象被激活时，**由 NT 内核直接将完成包排入 IOCP 队列**；
* **Win7 的缺失**：Windows 7（NT 6.1）的内核中完全不存在该内核对象模型。缺少该机制后，Bun 的事件调度循环无法将非 I/O 同步对象与网络 IOCP 无缝结合，极易导致事件丢包、调度器死锁或内部异常退出。

---

### 缺陷 2：Winsock 内核驱动（`afd.sys`）状态机脱节（入站 TCP RST 死穴）

这是导致 `Bun.serve()` 服务端在 Win7 下所有入站连接 100% 失败的**最致命缺陷**。

#### 1. 实验抓包与复现证据
前台启动监听服务后，使用 Curl 向其发起最简单的 HTTP 请求：
```bat
curl -v http://127.0.0.1:49374/
```
结果极其确凿：
```text
*   Trying 127.0.0.1:49374...
* Connected to 127.0.0.1 (127.0.0.1) port 49374
* using HTTP/1.x
> GET / HTTP/1.1
> Host: 127.0.0.1:49374
> User-Agent: curl/8.10.1
* Recv failure: Connection was reset
* closing connection #0
curl: (56) Recv failure: Connection was reset
```
**现象分析**：
- TCP 三次握手成功（`Connected to 127.0.0.1 port 49374`），说明套接字 `bind` 与 `listen` 阶段正常；
- 客户端发送请求报文后，服务端底层**未发出任何 HTTP 响应数据，而是立刻发送了一个 TCP RST 报文**强行重置连接。

#### 2. 深层机理（现代 `libuv` 与 Win7 `afd.sys` 的历史包袱）
* 在异步套接字处理中，Windows 依赖 `AcceptEx` 接收连接。连接完成后，必须调用：
  ```c
  setsockopt(accept_socket, SOL_SOCKET, SO_UPDATE_ACCEPT_CONTEXT, (char*)&listen_socket, sizeof(listen_socket));
  ```
  更新上下文，套接字才能正确进入已连接状态；
* 历史上，`libuv` 为了兼容 Windows 7 和 Vista，在 `src/win/tcp.c` 中维护了大量复杂的防御性代码，专门修补 Win7 `afd.sys` 在 `AcceptEx` 和重叠 I/O（Overlapped I/O）完成时的时序不一致与 spurious error；
* **兼容断层**：随着 `libuv` 官方正式放弃 Windows 7 支持（相关 Issue #2821 / #3260），**上述针对 Win7 `afd.sys` 的专用规避逻辑被大量清理**，代码完全按照 Windows 10 1709/1809 的驱动预期重写；
* 当基于新版 `libuv` 编译的 Bun 在 Win7 上运行时，Win7 `afd.sys` 返回的驱动层状态与新版状态机预期不符，`libuv` 的 `uv__process_tcp_accept_req` 或随后的 `WSARecv` 判定发生了不可恢复的严重套接字错误，立即触发硬关闭（`closesocket` 带未决数据产生 RST），将刚进来的连接强行掐断。

---

### 缺陷 3：现代套接字控制码（IOCTL）与协议选项不支持

Bun 在构建网络连接时，主动调用了多项仅在 Windows 10 现代版本中支持的 Winsock 控制码与套接字选项：

| 控制码 / 套接字选项 | 引入版本 | 在 Bun 中的作用 | Windows 7 下的行为与危害 |
| :--- | :--- | :--- | :--- |
| **`SIO_TCP_INITIAL_RTO`** | Windows 10 (1709+) | 配合 `TCP_INITIAL_RTO_NO_SYN_RETRANSMISSIONS`，用于本地回环（`127.0.0.1` / `::1`）连接失败时毫秒级即时报错，避免 Win7 默认重试等待 2 秒 | Win7 驱动返回 `WSAEOPNOTSUPP` (10045) 或 `WSAEINVAL` (10022) |
| **`SIO_LOOPBACK_FAST_PATH`** | Windows 8 / Server 2012 | 开启 TCP 回环快速通道，绕过 TCP/IP 完整协议栈开销提升本地吞吐 | Win7 不支持，若未做安全容错将导致套接字配置失败 |
| **`SO_REUSE_UNICASTPORT`** | Windows 10 (1607+) | 允许复用单播端口，提升并发连接吞吐 | Win7 返回 `WSAENOPROTOOPT` (10042) |
| **`WSHGetBroadcastSockaddr`** | Windows 8+ (`wship6.dll`) | IPv6 广播地址辅助解析函数 | Win7 的 `wship6.dll` 缺少此导出，导致 IPv6 初始化阶段报错 `0xc0000139` |

---

### 缺陷 4：出站代理隧道与 TLS 握手重置（Proxy Connect Reset）

在出站网络层面（例如检查云端更新、请求 OpenAI/Anthropic 模型 API），Bun 在配置了 `HTTP_PROXY` 时表现极其脆弱：
* **现象**：日志频繁记录：
  ```text
  message="update check failed" error="Error: Failed to check for updates (cause: TypeError: Unable to connect. Is the computer able to access the url?)"
  ```
* **机理**：
  通过 HTTP 代理隧道发起 HTTPS 连接需要经过两步：
  1. 向代理服务器发送 `CONNECT host:443 HTTP/1.1`；
  2. 收到 `200 Connection Established` 后，在该套接字上升级发起 TLS Client Hello 握手。
  在 Windows 7 上，由于底层套接字状态机在非阻塞切换与重叠 I/O 状态通知上的差异，Bun 在收到代理的 200 响应并尝试启动 TLS 握手时，再次触发了套接字重置，表现为代理隧道建立即断开。

---

### 缺陷 5：操作系统版本检测穿透（`ntdll.RtlGetVersion` 绕过用户态伪装）

* **现状**：
  许多用户态兼容层（包括 VxKex 的常规配置）重点拦截并伪装 Win32 API：`GetVersionExA`、`GetVersionExW` 和 `VerifyVersionInfoW`；
* **穿透现象**：
  因为微软自 Windows 8.1 起废弃了 `GetVersionEx`，现代跨平台基础设施（`libuv`、Rust `mio`、Zig 标准库）**全面绕过 Win32 层，直接通过 `GetProcAddress(ntdll, "RtlGetVersion")` 调用 NT 原生内核导出**；
* **后果**：
  Win7 系统自带的 `ntdll.RtlGetVersion` 始终诚实地返回 `dwMajorVersion = 6, dwMinorVersion = 1, dwBuildNumber = 7601`。这使得底层库在初始化阶段就准确获知当前运行于 Windows 7，从而在代码分支中提前禁用了关键功能，甚至直接抛出不受支持的错误。

## 四、VxKex 用户态兼容层的能力边界评估

针对上述五大缺陷，深入评估“能否通过扩展 VxKex 兼容层彻底修复 Bun”：

### 1. 用户态可做且已验证的修补（低~中难度）
* **`KxNt.dll` 拦截 `RtlGetVersion`**：
  在 VxKex 的 `KxNt` 中实现 `Ext_RtlGetVersion`，替换原有直接转发给系统 `ntdll` 的导出，对外部调用伪装返回 Windows 10 1809（`10.0.17763`），堵住版本检测穿透漏洞；
* **`KxNet.dll` 拦截非致命 IOCTL 与 SockOpt**：
  在 `Ext_WSAIoctl` 与 `Ext_setsockopt` 中，针对 `SIO_TCP_INITIAL_RTO`、`SIO_LOOPBACK_FAST_PATH`、`SO_REUSE_UNICASTPORT` 等调用进行拦截并假装返回成功（`return 0`），消除初始化阻断；
* **补齐基础用户态 API**：
  补齐 `VirtualAlloc2`、`VirtualAlloc2FromApp`、`FlsGetValue2` 以及 `wship6.dll` 中的 `WSHGetBroadcastSockaddr` 等缺失导出。

### 2. 用户态绝对无法突破的物理边界（根本性硬阻断）
1. **纯用户态无法伪造内核级 Wait Completion Packet**：
   `NtAssociateWaitCompletionPacket` 需要操作系统内核在内核对象变为 Signaled 时自动向 IOCP 派发包。在用户态即使写一个空的 Stub 函数返回 `STATUS_SUCCESS`，当真实的等待事件到来时，由于内核没有这个挂接机制，内核的 `GetQueuedCompletionStatusEx` 永远不会被唤醒，程序将陷入彻底的永久死锁；
2. **纯用户态无法重写 `afd.sys` 异步完成模型**：
   入站 TCP RST 是由内核网络驱动 `\Device\Afd` 与协议栈根据其自身状态机发出的。纯用户态 DLL 重写无法改变内核驱动处理 TCP 重叠 I/O 完成与上下文更新的时序。除非编写并安装一个 Windows 核心态过滤驱动（Kernel-mode Filter Driver），但这已经完全违背了 VxKex 作为“免驱动、纯用户态安全垫片”的基本架构定位。

## 五、主流 AI 终端工具在 Win7 兼容层下的表现对比

为了给工程实践提供明确参考，我们将当前主流 AI 编码工具在 Windows 7（结合 VxKex）下的底层网络兼容性进行对比：

| 工具名称 | 核心语言 / 运行时 | 网络与事件循环模型 | Win7 兼容度 | 根因与使用建议 |
| :--- | :--- | :--- | :---: | :--- |
| **OpenCode** | **Bun** | 前后端微服务架构，强依赖本地 `Bun.serve()` HTTP 通信 | **0%（完全不可用）** | `uSockets` + `libuv` 在 Win7 上 100% 触发 TCP RST，本地微服务彻底瘫痪 |
| **Claude Code** | **Bun** | 客户端命令行架构，走 Webview 进程与 IPC 管道 | **70%（API 模式可用）** | 网页 OAuth 依赖本地回调（受 TCP RST 影响失败），但通过 `ANTHROPIC_API_KEY` 直接出站可正常工作 |
| **Codex** | **Rust** | 标准同步/异步 `mio` 线程模型，依赖标准 Win32 API | **100%（完全可用）** | 无 Win10 专有网络驱动依赖，配置证书与代理后所有功能（终端、登录、Webview）均完美运行 |
| **Antigravity** | **Node.js** | 成熟的 libuv 兼容栈 + 内嵌 Chromium 环境 | **100%（完全可用）** | 自带独立 CA 证书链与现代代理栈，无任何驱动级兼容障碍 |

## 六、工程应对建议与技术路线推荐

基于上述深入排查结论，针对受 Bun 网络缺陷影响的场景，提出以下落地建议：

### 建议一：放弃在 Win7 本地运行基于 Bun 的自建 Web/RPC 服务
* 明确技术边界：不要试图通过打补丁的方式在 Win7 上解决 `Bun.serve()` 的入站 TCP RST 问题。这是一个跨越内核驱动、NT 调度器与现代网络库的系统性代差，强行修补会导致不可预测的死锁与数据损坏。

### 建议二：采用前后端解耦的“远程服务模式”（推荐解法）
OpenCode 等现代 AI 工具在架构上均天然支持前后端分离：
1. 将 `opencode serve` 服务端部署在局域网内任意一台 Linux 主机、WSL 或 Windows 10/11 机器上：
   ```bash
   opencode serve --port 4096
   ```
2. 在 Windows 7 本机仅将其作为轻量客户端运行：
   ```bat
   opencode --server http://192.168.x.x:4096
   ```
   或者直接在 Win7 机器上使用现代浏览器访问其 Web 界面。此方案无需修改一行源码，彻底绕开了 Win7 本机的 Bun 网络服务端缺陷。

### 建议三：优先选用基于 Rust 或 Node.js 的原生生产力工具
* 在 Windows 7 平台开展 AI 辅助研发工作时，建议优先选择底层网络栈成熟、对老版本 Windows 容错优秀的工具：
  - 首选 **Codex**（Rust 编写，资源占用极低，已在本项目中完全调优验证）；
  - 首选 **Antigravity**（成熟稳定，代理与认证机制完备）。
