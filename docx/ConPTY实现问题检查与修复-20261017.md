## 二、已正确实现的部分

1. **导出与 API Set 映射**：
   - `KxBase.dll` 导出 `CreatePseudoConsole`、`ResizePseudoConsole`、`ClosePseudoConsole`，并将 `InitializeProcThreadAttributeList`、`UpdateProcThreadAttribute`、`DeleteProcThreadAttributeList`、`CreateProcessA/W/AsUserW`、`GetConsoleMode`、`SetConsoleMode`、`CloseHandle`、`FreeConsole` 指向 `Ext_*` 实现。
   - `KxAdvapi.dll` 将 `CreateProcessAsUserW` 转发至 `KxBase.CreateProcessAsUserW`。
   - `KexDll` 的 API Set 前缀规则已将 `api-ms-win-core-console-l1-2-0` / `l1-2-1` 重定向到 `KxBase.dll`。
2. **基础参数校验与句柄校验**：
   - `CreatePseudoConsole` 对 `PseudoConsoleHandle == NULL`、`Size.X <= 0 || Size.Y <= 0`、非法 `Flags`、`NULL` 句柄及 `INVALID_HANDLE_VALUE` 进行了拦截。
   - 使用 `KEX_PSEUDOCONSOLE_MAGIC` (`0x4350584B`) + 全局链表 `KxPseudoConsoles` + `KxPseudoConsoleLock` 保护对象生命周期。
   - `Ext_UpdateProcThreadAttribute` 同时支持 `Value = hPC` 与 `Value = &hPC`（带 SEH 保护）。
   - `ClosePseudoConsole` 将已绑定的属性表槽标记为 `INVALID_HANDLE_VALUE`，阻止关闭后使用旧属性表静默创建无控制台进程。

## 三、检查发现的缺陷清单

### 问题 1（高危）：`ClosePseudoConsole` 未终止关联子进程，导致管道读端无法收到 EOF 且残留子进程（违反测试计划 C4）

- **位置**：`01-Extended DLLs\KxBase\console.c`（`ClosePseudoConsole`）、`01-Extended DLLs\KxBase\process.c`（`Ext_CreateProcess*`）
- **现象与根因**：
  - [ConPTY 正确性测试计划](ConPTY正确性测试计划-20261013.md) 用例 **C4** 要求：`ClosePseudoConsole` 之后，读端收到 EOF（`ReadFile` 返回 `0` / `ERROR_BROKEN_PIPE`），子进程被正确终止，不残留进程。
  - 在原生 Windows 10 ConPTY 中，`ClosePseudoConsole` 会关闭 `conhost.exe` 并终止挂载在该伪控制台下的客户端子进程，从而释放子进程持有的输出管道写端，使父进程阻塞的 `ReadFile` 立即收到 `ERROR_BROKEN_PIPE`（EOF）。
  - 在基线实现中，子进程（例如交互式 `cmd.exe`）通过 `STARTF_USESTDHANDLES` 继承了输出管道写端句柄；当父进程调用 `ClosePseudoConsole` 时，仅关闭了父进程内部的 `PseudoConsole->hInput` / `PseudoConsole->hOutput`，**并未记录或终止关联子进程**。
  - 結果：子进程继续存活并持有输出管道写端，父进程的 `ReadFile(outPipeRead)` 永久阻塞无法收到 EOF，且产生孤儿进程。

### 问题 2（中危）：`Ext_InitializeProcThreadAttributeList` 无条件占用 64 槽位，可能耗尽并导致普通进程创建失败

- **位置**：`01-Extended DLLs\KxBase\process.c`（`Ext_InitializeProcThreadAttributeList`、`KxBasepRememberPseudoConsoleAttribute`）
- **现象与根因**：
  - 每次调用 `InitializeProcThreadAttributeList`（即使完全不使用 ConPTY）都会在 64 大小的静态表 `KxPseudoConsoleAttributeEntries` 中占用一个槽位。
  - Windows 原生 `DeleteProcThreadAttributeList` 是空操作（no-op），许多第三方库直接 `free` 属性表内存而不调用 `DeleteProcThreadAttributeList`。一旦累计满 64 次，后续进程内**所有** `InitializeProcThreadAttributeList` 都会报 `ERROR_NOT_ENOUGH_MEMORY` 失败。

### 问题 3（中危）：未经 `Ext_InitializeProcThreadAttributeList` 登记的属性表默认 `NativeAttributes = TRUE` 导致 `CreateProcess` 失败

- **位置**：`01-Extended DLLs\KxBase\process.c`（`KxBasepRememberPseudoConsoleAttribute`）
- **现象与根因**：
  - 若调用方通过原生 `kernel32!InitializeProcThreadAttributeList` 初始化属性表（或槽位被回收后重新登记），再调用 `Ext_UpdateProcThreadAttribute` 仅设置 `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`，基线代码会将 `Entry->NativeAttributes` 保守设为 `TRUE`。
  - 由于 `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` 被拦截而未写入 Win7 原生属性表，此时原生属性表实际计数为 0；而 `NativeAttributes == TRUE` 导致 `KxBasepPreparePseudoConsole` 不剥离 `EXTENDED_STARTUPINFO_PRESENT`，Win7 原生 `CreateProcess` 检查到空属性表直接返回 `ERROR_INVALID_PARAMETER (87)`。

### 问题 4（低危）：子进程 `hStdOutput` 与 `hStdError` 共用同一句柄值，且未清除 `DETACHED_PROCESS`

- **位置**：`01-Extended DLLs\KxBase\process.c`（`KxBasepPreparePseudoConsole`、`KxBasepReleaseStartupHandles`）
- **现象与根因**：
  - `StartupInfo->hStdOutput` 与 `StartupInfo->hStdError` 被赋为同一个 `Output` 句柄值；若子进程单独关闭 `stdout` 句柄，会连带关闭 `stderr` 底层句柄。
  - 创建标志改写 `*CreationFlags = (*CreationFlags & ~CREATE_NEW_CONSOLE) | CREATE_NO_WINDOW` 未清除 `DETACHED_PROCESS`（`DETACHED_PROCESS` 与控制台标志冲突或导致子进程无法打开 `CONOUT$`）。
  - 另外，`CreatePseudoConsole` 未拦截 `NtCurrentThread()` (`(HANDLE)(LONG_PTR)-2`) 伪句柄。

### 问题 5（低危）：`Ext_CloseHandle` 全局锁包裹系统调用，且 `SetConsoleMode` 的全局 ANSI 状态跨句柄互相覆盖

- **位置**：`01-Extended DLLs\KxBase\console.c`（`Ext_CloseHandle`、`Ext_SetConsoleMode`、`Ext_WriteConsoleA/W`）
- **现象与根因**：
  - `Ext_CloseHandle` 在调用 `CloseHandle(Handle)` 期间全程持有排他锁 `KxConsoleModeLock`，导致进程内所有文件、管道、事件句柄的关闭都被串行化。
  - `Ext_SetConsoleMode` 在任意一个输出句柄（如 `stderr`）未设置 `ENABLE_VIRTUAL_TERMINAL_PROCESSING` 时，会调用 `BaseDisableConsoleAnsiSupport` 关闭全局 `g_ConsoleANSISupport`，导致另一个已开启 VT 的输出句柄（如 `stdout`）失去 ANSI 转义序列解析能力。

### 问题 6（致命，部署后暴露）：部分替换或全量复制 `x64\Release` 编译产物后 VS Code 均无法启动

- **位置**：`01-Extended DLLs\KxBase\console.c`、`01-Extended DLLs\KxBase\process.c`、`01-Extended DLLs\KxBase\kxbase.def`、`01-Extended DLLs\KxBase\forwards.c`、`01-Extended DLLs\KxAdvapi\forwards.c` 以及安装目录结构。
- **触发场景**：无论是仅替换 `C:\Program Files\VxKex\Kex64\` 下的 `KxBase.dll` + `KxAdvapi.dll`，还是将 `D:\project\VxKex-NEXT\x64\Release\` 下所有编译产物直接覆盖到安装目录，VS Code（`Code.exe`，Electron/Chromium 架构）均无法启动；卸载并重装官方安装包后恢复正常。
- **完整根因分析**：
  1. **为什么把 `x64\Release\*` 所有编译文件直接复制到 `C:\Program Files\VxKex\Kex64\` 会导致崩溃？**
     - MSBuild 的 `D:\project\VxKex-NEXT\x64\Release\` 是扁平输出目录，混放了安装时属于**三个不同系统目录**的组件（见 `KexSetup\perform.c`）：
       - `C:\Windows\System32\KexDll.dll`（及 32 位 `SysWOW64\KexDll.dll`）：由 `ntdll.dll` Application Verifier 在进程初始化最早期直接从 `System32` 加载并初始化全局 `KexData`。
       - `C:\Program Files\VxKex\`：`KexCfg.exe`、`VxKexLdr.exe`、`VxlView.exe`、`KexShlEx.dll`、`CpiwBypa.dll`。
       - `C:\Program Files\VxKex\Kex64\`：`Kx*.dll` 扩展 DLL、`KexW32ML.dll` 以及 `02-Prebuilt DLLs\x64\` 下的预编译运行库（`dwrite.dll`、`d3dcompiler_47.dll`、`ucrtbase.dll` 等）。
     - 若将 `x64\Release\KexDll.dll` 复制进 `C:\Program Files\VxKex\Kex64\`，由于 `Kex64` 被前置到进程 `DllPath`，当加载 `KxBase.dll` 等扩展 DLL 时，其对 `KexDll.dll` 的静态导入会解析到 **`Kex64\KexDll.dll`（进程内的第二份 `KexDll.dll` 副本）**，而该副本从未经过 `DLL_PROCESS_VERIFIER` 初始化，其内部 `KexData` 为 `NULL`，一调用 `KexDataInitialize` / `KexLog*` 即触发空指针访问违例崩溃。
     - 因此，全量升级必须通过编译生成的自解压安装程序 **`KexSetup_Release.exe`** 执行（自动处理正在使用文件的事务改名替换 `KexSetupSupersedeFile`、三目录分发及 `KexSetupApplyAclToFile` 权限设置）。
  2. **为什么只替换 `KxBase.dll` 与 `KxAdvapi.dll` 也会导致 VS Code 无法启动？**
     - **根因 A（`CloseHandle` 导出钩子破坏 Chromium `ScopedHandleVerifier`）**：基线 `f98d857` 中 `CloseHandle` 是直接转发到 `kernel32.CloseHandle` 的 PE 导出转发器（Export Forwarder）。此前修改将其改为 `KxBase!Ext_CloseHandle` 函数导出，不仅在每次关闭任意句柄时争用 `KxConsoleModeLock`，而且破坏了 Electron/Chromium（`Code.exe` 导出 `GetHandleVerifier`）启动时 `CloseHandleHooks` / `ScopedHandleVerifier` 对 `CloseHandle` 模块归属与指令的校验。
     - **根因 B（`CreateProcessAsUserW` 跨 DLL 转发与延迟加载/动态查找风险）**：在 Win7 SP1 上，`kernel32.dll!CreateProcessAsUserW` 是指向 `API-MS-Win-Security-Base-L1-1-0.dll` 的延迟加载桩（在 VxKex 下被 `KexLdrResolveDelayLoadedAPI` 重写回 `kxbase.dll` 导致无限递归栈溢出）；同时将 `KxAdvapi.CreateProcessAsUserW` 改写为转发到 `KxBase.CreateProcessAsUserW` 会拦截 Chromium Sandbox Broker 创建 GPU/Renderer 沙箱子进程的所有调用。
     - **根因 C（非 ConPTY 进程无条件加锁与属性表插桩）**：VS Code 主进程及沙箱在启动 GPU/Renderer 子进程时高频调用 `InitializeProcThreadAttributeList`、`UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY / HANDLE_LIST)` 与 `CreateProcess*`。此前实现即使在从未调用过 `CreatePseudoConsole` 的进程中也无条件加排他锁 `KxPseudoConsoleLock`、分配 64 槽位并复制 `STARTUPINFOEX`。

## 四、结合 4 个核心开源参考实现的修复方案

参考微软官方 `winconpty.cpp` / `EchoCon.cpp`、Wine `dlls/kernelbase/console.c` & `process.c`、VxKex-NEXT `apiset.c` / `redirects.h` 以及 Rust `wezterm` (`portable-pty`) / `conpty` crate 源码，完成如下修复：

1. **恢复 `CloseHandle` 与 `KxAdvapi!CreateProcessAsUserW` 原生导出转发（100% 对齐 `f98d857` 基线）**：
   - 在 `01-Extended DLLs\KxBase\forwards.c` 恢复 `#pragma comment(linker, "/EXPORT:CloseHandle=kernel32.CloseHandle")`，从 `kxbase.def` 移除 `CloseHandle = Ext_CloseHandle`。
   - 在 `01-Extended DLLs\KxBase\console.c` 的 `KxBasepHasEmulatedAnsiOutputLocked` 与 `Ext_SetConsoleMode` 中通过 `GetConsoleMode` 惰性清理已关闭的控制台句柄槽位，无需拦截全局 `CloseHandle`。
   - 在 `01-Extended DLLs\KxAdvapi\forwards.c` 恢复 `#pragma comment(linker, "/EXPORT:CreateProcessAsUserW=advapi32.CreateProcessAsUserW")`，使 `KxAdvapi.dll` 与官方 1.2.3.2463 完全一致。
2. **直接静态导入原生 `CreateProcessW/A/AsUserW` 并增加 `KxPseudoConsoleInitialized` 零开销快路径**：
   - 根据 `KexDll\dllrewrt.c` 的 `KexShouldRewriteStaticImportsOfDll`，`Kx*.dll` 自身的静态导入表永远不会被 VxKex 重写。因此在 `01-Extended DLLs\KxBase\process.c` 中通过 `#pragma comment(lib, "advapi32.lib")` 及 `kernel32` 导入库直接调用原生 `CreateProcessW`、`CreateProcessA`、`CreateProcessAsUserW`，彻底移除动态 `LdrGetProcedureAddress` 查找。
   - 新增 `volatile LONG KxPseudoConsoleInitialized` 标志（仅在进程首次调用 `CreatePseudoConsole` 时置为 `1`）。对于从未调用 `CreatePseudoConsole` 的普通进程（如 VS Code 主进程、GPU 进程、Renderer 进程），`Ext_InitializeProcThreadAttributeList`、`Ext_DeleteProcThreadAttributeList`、`Ext_UpdateProcThreadAttribute`、`Ext_CreateProcessW/A/AsUserW` **100% 原生直通（零加锁、零属性表记录、零 `STARTUPINFOEX` 拷贝）**。
   - 即使在启用了 ConPTY 的进程中，`Ext_InitializeProcThreadAttributeList` 也只清理已存在的复用槽位而不预占新槽位，仅在 `UpdateProcThreadAttribute` 实际绑定 `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`（或活动 ConPTY 下的 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`）时才分配槽位，且不在调用系统 `UpdateProcThreadAttribute` 期间持有 `KxPseudoConsoleLock`。
3. **对齐 `winconpty.cpp`、Wine 与 Rust `portable-pty` 的句柄继承与启动参数契约**：
   - **主句柄非继承 + 启动句柄可继承**：在 `CreatePseudoConsole` 中调用 `DuplicateHandle(..., FALSE, DUPLICATE_SAME_ACCESS)` 保存内部主管道句柄（防止父进程创建其他无关子进程时泄漏管道写端导致无法收到 EOF）；在 `KxBasepPreparePseudoConsole` 中为子进程 `hStdInput`、`hStdOutput`、`hStdError` 分别调用 `DuplicateHandle(..., TRUE, DUPLICATE_SAME_ACCESS)` 生成可继承句柄，并在 `CreateProcess*` 返回后立即由 `KxBasepReleaseStartupHandles` 关闭父进程侧临时副本。
   - **兼容 Rust `portable-pty` / C++ 双传参模式与 `INVALID_HANDLE_VALUE` 覆盖**：`Ext_UpdateProcThreadAttribute` 同时支持 `lpValue = hPC`（Rust `portable-pty` / `conpty` crate）与 `lpValue = &hPC`（C/C++ 封装）；`KxBasepPreparePseudoConsole` 在局部 `LocalStartupInfoEx` 副本上覆写 `hStdInput/Output/Error`（兼容 `wezterm` 预填 `STARTF_USESTDHANDLES` + `INVALID_HANDLE_VALUE` 的做法），并通过 `STARTF_USECOUNTCHARS` 传递 `PseudoConsole->Size`，完全不修改调用方传入的 `STARTUPINFOEX` 内存。
   - **子进程跟踪与 `ClosePseudoConsole` 终止保障（测试计划 C4）**：在 `KEX_PSEUDOCONSOLE` 中记录挂载的子进程句柄，`ClosePseudoConsole` 时终止仍存活的关联子进程并释放管道写端，确保读端立即收到 `ERROR_BROKEN_PIPE`（EOF）。
